# Framework and CLI research

**Research date: 2026-10-20. Verdict: choose TanStack Start (React) for the product application, with a separate Node/container crawler worker.** Astro is excellent for a content-heavy marketing site, but this product is principally an interactive React application with typed server calls, client state, and HTTP streaming. TanStack Start is stable as of Oct 13, 2026; pin a current patched 1.x release (the latest release found during research was `@tanstack/react-start@1.169.3`). Do not deploy an older Start version: the Sep 30 server-function XSS fix begins at `1.168.60` ([release/security note](https://tanstack.com/blog/tanstack-start-security-update-cve-2026-102989), [stable announcement](https://tanstack.com/blog/tanstack-start-1-0)).

## 1. Framework choice

### Recommendation

- **Web app:** React 19.2, TanStack Start 1.x / TanStack Router 1.x, Vite 8-compatible current Start scaffold; Tailwind CSS 4, shadcn/ui (React/Radix primitives), TanStack Query for server state, and React state for local report interactions. Current repo already uses React 19.2, Tailwind 4, and Zod 4, so these choices preserve useful investments.
- **Server boundary:** use Start server functions for same-origin typed actions (create audit, read report, auth-gated data); use Start server routes for public HTTP endpoints and raw SSE `Response` streams. Server functions support typed `ReadableStream`/async-generator results, while server routes allow standard `text/event-stream`, headers, cancellation, and `Last-Event-ID` handling ([server functions](https://tanstack.com/start/latest/docs/framework/react/guide/server-functions), [typed streaming](https://tanstack.com/start/latest/docs/framework/react/guide/streaming-data-from-server-functions), [server routes](https://tanstack.com/start/latest/docs/framework/react/guide/server-routes)).
- **Long jobs:** request handler validates, persists a job, enqueues it, and immediately returns an audit ID. A worker does crawling/checks/LLM calls. Persist progress/events in the database; SSE reads that durable state/event log. Do not hold one server function or HTTP request open for a 30-second to 5-minute audit.
- **Auth:** Better Auth has a first-party TanStack Start integration and documented server-function session checks; enforce authorization in every data endpoint/function, not only route navigation ([Better Auth integration](https://better-auth.com/docs/integrations/tanstack), [Start security guidance](https://tanstack.com/start/latest/docs/framework/react/guide/server-functions)).
- **Marketing SEO:** Start provides full-document SSR, metadata/head management, route loaders and streaming; it can render crawlable marketing pages and the app. Astro has the edge in static/content-first authoring and minimal client JS, but this tool's dense, stateful report UI benefits more from React-first composition than from Astro islands.

### Astro v5/v6 versus current Astro

Astro 5 and 6 are capable choices, and Astro 6 added a substantial dev/build-runtime refactor and improved Workers support. However, by this research date **Astro 7.4 is current** (released Oct 15, 2026), so do not start a new build on v5/v6 unless a dependency requires it. Astro 7 adds Vite 8/Rolldown, Rust compilation, and advanced routing; it remains oriented toward content sites with opt-in UI framework islands ([Astro 6](https://astro.build/blog/astro-6/), [Astro 7](https://astro.build/blog/astro-7/), [Astro 7.4](https://astro.build/blog/astro-740/)).

Astro features relevant here:

- **Server islands** defer personalized/dynamic HTML behind a fallback; they are not a durable job system or substitute for interactive report state ([server islands](https://docs.astro.build/en/guides/server-islands/)).
- **Actions** provide Zod-validated, typed backend calls, and adapters enable on-demand rendering. Actions are public endpoints and require explicit authorization checks ([actions](https://docs.astro.build/en/guides/actions/), [on-demand rendering/adapters](https://docs.astro.build/en/guides/on-demand-rendering/)). Astro also exposes API routes, so raw SSE is possible, but the React client and API contracts would need more manual assembly than Start's cohesive React router/server-function setup.
- **Deployment:** official Node, Vercel, and Cloudflare adapters exist. Astro's Cloudflare adapter now targets Workers; browser crawling still belongs in a Node/container or remote-browser service ([adapter list](https://docs.astro.build/en/guides/on-demand-rendering/), [Cloudflare adapter](https://docs.astro.build/en/guides/integrations-guide/cloudflare/)).

### TanStack Start fit and trade-offs

Start is a stable full-stack React framework with SSR, streaming, server functions, server routes, middleware, and file-based type-safe routes ([overview](https://tanstack.com/start/latest/docs/framework/react/overview)). Server functions are typed RPC and handle serialization; server routes are proper raw endpoints. This division maps cleanly to audit creation and SSE. Loaders, route/search parameter types, and server-function input/return types create useful compile-time flow, but runtime validation is still required for external input and persisted data. Treat server functions as network endpoints, not private in-process calls.

Vite-based Start supports deployment to Node/server, Docker and platform runtimes; official examples/docs include Cloudflare and Vercel integrations, and the framework is designed for deployment flexibility ([deployment docs](https://tanstack.com/start/latest/docs/framework/react/guide/deployment), [Cloudflare example](https://tanstack.com/start/latest/docs/framework/react/examples/start-basic-cloudflare)). For Vercel/Node/Docker, keep Playwright in the separately scaled worker. Cloudflare Queues can deliver jobs to Workers, but a Worker consumer is a poor fit for full Chromium; use HTTP pull from a Node worker or use a separate container queue/worker. Cloudflare Queue consumer wall time is capped at 15 minutes, yet execution environment constraints still matter ([Queues limits](https://developers.cloudflare.com/queues/platform/limits/), [HTTP pull consumers](https://developers.cloudflare.com/queues/configuration/pull-consumers/)).

**Maturity:** Astro is older and very established. Start reached 1.0 only on Oct 13, 2026, so its stable contract is new despite extensive pre-1.0 production usage. Use current patched releases, keep a lockfile, and monitor release/security notes. Its React/client-first architecture, recent stability milestone, and direct typed streaming outweigh Astro's longer history for this workload.

## 2. Monorepo and job architecture

```text
apps/
  web/                 # TanStack Start UI, API/server routes, auth, SSE
  cli/                 # published audit CLI; depends on @product/core
  worker/              # Node/container queue consumer; Playwright + audit orchestration
packages/
  core/                # framework-free TS: URL policy, crawl/check models,
                       # deterministic checks, scoring, fix-prompt Markdown
  contracts/           # shared Zod schemas and API/event types (optional;
                       # fold into core until there is a real boundary)
```

Use Bun package.json workspaces (`apps/*`, `packages/*`), package-local dependency declarations, and `workspace:*` for internal packages; build/publish `core` as an ordinary ESM package so both CLI and worker can run under Node/Bun. Bun officially supports npm workspaces; keep the crawler Node-compatible rather than relying on Bun-specific browser behavior ([Bun workspaces](https://bun.sh/docs/pm/workspaces), [workspace guide](https://bun.sh/guides/install/workspaces)).

**A queue is necessary** because requests can take minutes and require retries, backpressure, idempotency, and durable progress. Start with one durable jobs table plus one queue. For a Node/container-first deployment, choose **BullMQ + managed Redis**: mature worker/job model, retries/backoff, delays and concurrency controls ([BullMQ queues](https://docs.bullmq.io/guide/queues/), [workers](https://docs.bullmq.io/guide/workers/)). If Cloudflare is the chosen hosting platform, Cloudflare Queues is a minimal managed alternative; attach a pull consumer to the external Node worker, or use Workers only for non-browser stages. Both are at-least-once systems: make audit stages idempotent and persist status/events in the database. For fastest managed orchestration/observability with little queue ops, evaluate Inngest or Trigger.dev; select one only if their hosted workflow value justifies the service dependency. Do not build a custom in-process queue.

Progress shape: durable `audit_events(audit_id, sequence, type, payload, created_at)` with monotonic sequence; SSE streams after `Last-Event-ID` and reconnects from storage. Worker emits bounded/sanitized events. Rate-limit audit creation by IP/account, cap pages/time/LLM spend, enforce tenant ownership, and apply SSRF defenses at every redirect and DNS resolution (block loopback, private, link-local, metadata IPs; restrict ports/protocols; defend DNS rebinding). Run browser processes as an unprivileged user with sandbox/seccomp in an isolated container; Playwright explicitly recommends this for untrusted crawl targets ([Playwright Docker security guidance](https://playwright.dev/docs/docker)).

## 3. CLI

**Pick Commander 15.x** for `audit <url>`, options, stable help/errors, command grouping, and broad community/ecosystem familiarity. It has TypeScript support and supports standalone subcommands; use `@commander-js/extra-typings` if inferred option types are valuable ([Commander README](https://github.com/tj/commander.js), [typed extras](https://github.com/commander-js/extra-typings)). For a small single-command binary, citty is a reasonable lighter alternative; `@clack/prompts` can add optional interactive setup without making CI/headless invocations interactive. Avoid oclif unless plugins, generated command trees, and a larger extension ecosystem justify its framework weight.

Ship `apps/cli` as an npm package with a `bin` entry (for example `"audit-site": "./dist/index.js"`), ESM output, Node `engines` matching the Playwright/Commander requirements, and a shebang. Publish a scoped package; users run `npx @scope/audit-site URL` or `bunx @scope/audit-site URL`. Keep `--json`, `--no-color`, exit codes, and non-interactive behavior stable. CLI calls the same core package directly; remote audit mode calls the web API, while local mode can execute available checks in-process.

## 4. TypeScript and quality tooling

- **TypeScript:** TypeScript 6.0 is current, with 7.0 positioned as the upcoming native compiler. Use the latest compatible 6.x and explicitly enable `strict`, `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`, `noImplicitOverride`, `noFallthroughCasesInSwitch`, `noImplicitReturns`, and `forceConsistentCasingInFileNames`; set `skipLibCheck: true`, `noEmit: true`, and package-appropriate `moduleResolution` (`Bundler` for Vite apps; `NodeNext` for published Node packages). Avoid deprecated `baseUrl`/legacy options during the TS6 transition ([TypeScript 6.0 release notes](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-6-0.html)). **TanStack-specific exception:** leave `verbatimModuleSyntax` disabled per its current setup guidance because it can cause server bundles to leak into client bundles; use explicit `import type` consistently instead ([Start setup](https://tanstack.com/start/latest/docs/framework/react/guide/build-from-scratch)).
- **Validation:** Zod 4 is stable and current; put schemas at trust boundaries (request input, queue payload, config, OpenRouter response, persisted JSON), infer TS types from schemas, and revalidate provider output before use ([Zod 4](https://zod.dev/v4), [Zod package](https://zod.dev/packages/zod)).
- **Lint/format:** Biome 2.5 is the lean default for TS/TSX/JSON formatting and linting. Keep `tsc --noEmit` separate: lint is not type checking. If React Compiler rules, specialized framework rules, or plugin coverage become necessary, use ESLint flat config plus Prettier instead of maintaining overlapping formatters ([Biome 2.5](https://biomejs.dev/blog/biome-v2-5/)).
- **Tests:** Vitest 5.0 is the latest major announced in 2026; use it with `defineConfig` from `vitest/config`, shared Vite config where practical, Node environment for core/worker tests, and jsdom or happy-dom only for UI tests. Keep deterministic check fixtures and mock network/browser/LLM boundaries ([Vitest blog/releases](https://vitest.dev/blog)).
- **Errors:** in `core`, use discriminated `Result` values for expected/domain outcomes (invalid target, unsupported page, partial check failure) so the CLI and worker handle them explicitly. Throw for truly exceptional failures at infrastructure/framework boundaries (DB down, browser crash); translate to stable public error codes at the boundary, redact secrets/internal details, and preserve causes in logs. Do not throw strings or expose raw provider errors.
